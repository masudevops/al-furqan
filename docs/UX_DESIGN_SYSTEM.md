# Al-Furqan UX and Design System

## Experience direction

Al-Furqan should feel calm, legible, reverent, and precise. Decoration supports orientation but never competes with Arabic text. The reading surface is the product’s visual center.

## Design principles

- Quran content receives the strongest typography and most whitespace.
- Controls become quieter while reading and remain easy to reveal.
- One primary action per region.
- Source and edition details are visible without feeling alarming.
- Differences in scholarly or calculation settings are explained neutrally.
- Mobile interactions work without hover.
- Dark mode preserves contrast and Arabic glyph clarity.

## Color roles

Use semantic tokens instead of page-specific Tailwind colors.

| Token | Purpose | Suggested light value |
|---|---|---|
| `surface-page` | Main background | warm neutral `#F8FAF8` |
| `surface-card` | Cards/dialogs | `#FFFFFF` |
| `surface-reader` | Quran reading paper | `#FFFCF2` |
| `text-primary` | Main text | `#17221C` |
| `text-secondary` | Metadata | `#5F6F65` |
| `brand` | Primary action | `#087A55` |
| `brand-subtle` | Selected/focus background | `#DDF4EA` |
| `accent-gold` | Sparing sacred/bookmark accent | `#B68A2E` |
| `danger` | Destructive/error | `#B42318` |
| `focus` | Keyboard focus ring | `#2563EB` |

Dark tokens should be separately designed, not generated by inversion. Meet WCAG 2.2 AA contrast.

## Typography

### Arabic Quran

- Use a licensed, verified Uthmani Quran font/dataset.
- Default reader size should be generous, adjustable, and stored as a preference.
- Apply `lang="ar"` and `dir="rtl"` to Arabic text.
- Avoid arbitrary letter spacing and text transforms.
- Test glyph rendering, ayah marks, pause signs, and line wrapping on target browsers.

### Arabic prose

Use a readable Naskh family distinct from the Quran font where appropriate.

### Interface and translations

Use a highly legible sans-serif. Suggested scale:

- Display: 40–48 px
- Page title: 28–32 px
- Section title: 20–24 px
- Body: 16–18 px
- Metadata: 13–14 px

Maintain comfortable line lengths: roughly 55–75 Latin characters for prose and a wider but controlled Quran reading measure.

## Spacing and layout

Use a 4 px base grid with common steps of 4, 8, 12, 16, 24, 32, and 48 px.

- Mobile page gutter: 16 px
- Tablet page gutter: 24 px
- Desktop content gutter: 32 px
- Reading width: 760–900 px depending on mode
- General app max width: 1200 px
- Minimum touch target: 44 × 44 px

Respect `env(safe-area-inset-*)` for sticky headers, bottom navigation, and audio controls.

## Core components

Create tested shared primitives:

- Button: primary, secondary, ghost, destructive
- IconButton: always requires an accessible label
- Dialog/Drawer: focus trap, Escape close, labelled title, focus restoration
- Tabs: keyboard arrow behavior and selected semantics
- Select/Combobox: searchable variant for Surahs and editions
- Card and ReaderSurface
- QuranAyah and WordToken
- ArabicText and TranslationText
- SourceBadge and ContentAttribution
- Toast and inline status message
- Skeleton, EmptyState, ErrorState, OfflineState
- Range/Slider for audio progress and font size
- BottomSheet for mobile study controls

## Quran reader patterns

### Reading mode

- Arabic first, translation optional.
- Ayah actions are available through a persistent or tap-revealed action row.
- Active audio ayah uses a subtle border/background rather than motion or scale.
- Preserve the user’s place when settings change.

### Study mode

- Word tokens are individually focusable only when interaction is enabled.
- Selecting a word opens a bottom sheet on mobile and side panel on desktop.
- Tafsir opens without navigating away from reading context.
- Source, author, language, and edition are always visible.

### Mushaf mode

- Prefer verified page assets or layout with stable dimensions.
- Pinch/zoom and page navigation must not interfere with browser accessibility.
- Provide a text-mode alternative.

## Navigation

### Mobile

Use a compact primary navigation of four or five destinations:

- Home
- Quran
- Prayer
- Library
- More

Bookmarks, settings, Hadith, Hisnul, and books can live in Library/More or contextual entry points. Avoid seven-item hidden menus as the only discovery mechanism.

### Desktop

Use a restrained top navigation plus global search and profile/settings. The Quran reader may use a secondary contextual toolbar.

## Interaction and motion

- Default transitions: 120–200 ms.
- Avoid scaling entire reading cards on hover.
- Do not animate auto-scroll if reduced motion is requested.
- Honor `prefers-reduced-motion`.
- Never rely on color, hover, or animation alone to convey state.

## Accessibility requirements

- WCAG 2.2 AA for core flows.
- Skip-to-content link and consistent landmarks.
- Visible focus indicator with at least 3:1 contrast.
- All icon buttons named with `aria-label`.
- Dialogs implement correct semantics and focus management.
- Status updates use appropriate live regions.
- Form errors are associated with fields.
- RTL and LTR are scoped at content boundaries.
- Audio is operable without a pointer.
- Touch-only users can access every action.
- Test at 200% zoom and 320 CSS px viewport width.

## Content and terminology

- Prefer “Quran” consistently; use “Al-Qur’an” only as a deliberate brand/style choice.
- Prefer “tafsir” as the English transliteration and preserve source spellings in titles.
- Explain Juz, Hizb, Qira’ah, Madhhab, and calculation methods in plain language.
- Avoid asserting “most authentic” or similar comparative claims without editorial approval and context.
- Religious quotations require a visible reference.

## Empty, error, and offline language

Messages should identify what failed and what the user can do:

- “We couldn’t load this translation. The Arabic text is still available.”
- “Prayer times are unavailable offline for this date. Reconnect or view your last saved schedule.”
- “This tafsir source does not include the selected ayah.”

Never render placeholder prose where Quran text is expected.

## UX review checklist

- Can the flow be completed one-handed on a phone?
- Are all actions visible without hover?
- Does keyboard order match visual order?
- Does Arabic render correctly at all supported sizes?
- Are content source and edition discoverable?
- Are loading, offline, empty, and error states designed?
- Do sticky elements overlap content or each other?
- Is personal/location data use explained before collection?
